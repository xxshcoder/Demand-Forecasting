------------------------------------------------------------

Built a production-style, end-to-end demand forecasting MLOps pipeline with DVC,
MLflow, Airflow, FastAPI, a promotion gate, prediction logging and drift monitoring;

served model returned predictions at 1,075 ms median latency in a local load test.

------------------------------------------------------------
4. RESUME BULLETS - DETAILED VERSION
------------------------------------------------------------

PROJECT OVERVIEW

- Designed and implemented a complete one-day-ahead demand forecasting system for
  store-item pairs, covering data versioning, cleaning, validation, feature
  engineering, model training, experiment tracking, model registry, gated
  promotion, REST serving, scheduled retraining, prediction logging, drift
  monitoring, testing and CI.

- Targeted Python 3.11 with pinned dependencies in `requirements.txt`,
  `requirements-dev.txt` and `requirements-serving.txt`; all model, split, data,
  monitoring and serving settings live in `params.yaml` with no hard-coded magic
  numbers in business logic.

DATA AND REPRODUCIBILITY

- Generated a deterministic synthetic fallback dataset (10 stores x 50 items x
  about five years, 908,442 raw rows after injected gaps) after Kaggle credentials
  were unavailable, with trend, weekly/yearly seasonality, holidays, promo effects,
  noise, missing days and outliers; labelled all runs `DATASET_LABEL=synthetic`.

- Tracked raw data with DVC and a local remote; Git stores only `.dvc` pointers,
  never raw CSVs, parquet data or secrets. `python -m dvc repro` builds
  `prepare -> features -> train -> evaluate -> compare`; final `dvc status` was
  clean, `dvc repro` was a no-op and `dvc push` was up to date.

- Implemented explicit pandas validation with `DataValidationError`: schema and
  dtype checks, non-null keys, non-negative sales, duplicate removal, configurable
  missing-day filling (`forward_fill` by default, `zero` tested), outlier clipping
  at the 0.999 quantile, uniqueness, sorted order and gap-free output.

FEATURE ENGINEERING AND LEAKAGE SAFETY

- Built one shared feature function used by both batch training and single-request
  serving to eliminate train/serve skew: store/item IDs, day of week, month, day of
  month, weekend flag, country holidays, lags 1/7/14/28 and rolling mean/std over
  7/14/28 days, plus optional price and promo.

- Used strictly time-based splits: train < test < validation. Final 90-day
  validation window contains 45,000 rows from 2018-10-03 to 2018-12-31; an extra
  90-day test window is held out from training and from neural-network early
  stopping.

- Added tests proving that changing `sales` on day t does not change any feature of
  day t, batch and serving features match for the same series/date, and split
  boundaries never overlap.

MODELLING AND EXPERIMENT TRACKING

- Trained and fairly scored five models on the same validation window: last-week
  baseline, moving-average baseline, Ridge, HistGradientBoostingRegressor and a
  PyTorch MLP with store/item embeddings and train-only early stopping.

- Logged exactly one MLflow run per model (five training runs total) with flattened
  parameters, `val_mae`, `val_rmse`, `val_mape`, `val_wape`, Git SHA, DVC data hash,
  model type and dataset tags, feature list, prediction sample, reference parquet
  and a versioned `mlflow.pyfunc` artifact with signature and input example.

- Best learned model was HGB with MAE 2.120, RMSE 3.033, MAPE 12.556% and WAPE
  11.970%; the PyTorch MLP was honestly reported as worse on MAE (2.257).

MODEL REGISTRY AND PROMOTION

- Registered models under `demand-forecaster` in MLflow and used registry aliases
  `production` and `candidate` instead of deprecated stages.

- Implemented a pure, testable promotion gate that rejects non-finite or missing
  metrics, requires the candidate to beat the best baseline, requires at least
  0.5% relative MAE improvement over the current production model and limits RMSE
  regression to 5%.

- Promoted HGB as production v1; later refused linear v2 with
  `-22.0767%` relative MAE improvement. Promotion verdicts are written to
  `reports/promotion_decision.json` and audited in a separate MLflow experiment so
  the training experiment stays at one run per model.

SERVING

- Built a FastAPI service with Pydantic v2 request/response contracts: `POST
  /predict`, `GET /health`, `GET /model-info` and token-protected `POST
  /admin/reload`.

- Enforced strict validation: positive integer store/item IDs, ISO date, exactly
  28 finite non-negative recent-sales values, optional finite non-negative price,
  promo in {0, 1}, rejection of unknown fields and HTTP 422 on invalid input.

- Loaded `models:/demand-forecaster@production`, cached it in memory and polled the
  alias every 60 seconds (`MODEL_REFRESH_SECONDS` override). Verified v1 -> v2 ->
  v1 alias changes were reflected by `/model-info` with no API restart.

- Captured real API responses in `reports/api_examples.md`, including prediction
  `7.36`, model version `1`, request ID, timestamp and validation metrics.

MONITORING

- Logged every prediction to a SQLAlchemy `prediction_logs` table with request ID,
  UTC timestamp, store/item, forecast date, computed features JSON, prediction,
  model version and latency; database failures are logged but never break a
  prediction.

- Implemented PSI with reference quantile bins and Kolmogorov-Smirnov statistics
  with p-values, with thresholds from `params.yaml` (`psi_threshold=0.2`,
  `ks_pvalue_threshold=0.01`, `psi_bins=10`, `recent_window_days=7`).

- Generated Markdown and HTML drift reports. 100 in-distribution requests produced
  no drift; 100 requests with recent sales multiplied by 2 flagged all 10
  sales-derived features (`lag_*` and `roll_*`) while ID/calendar features stayed
  stable.

ORCHESTRATION, CONTAINERS AND CI

- Authored a weekly Airflow DAG (`demand_forecast_retrain`, `catchup=False`, one
  retry) with seven thin tasks: ingest, validate, build_features, train, evaluate,
  compare and register_and_promote; all business logic stays in `src/`.

- Created Dockerfiles for the API and Airflow and a Docker Compose stack with
  Postgres, MLflow server, FastAPI, Airflow webserver and scheduler, health checks,
  shared artifact volume and databases for mlflow/airflow/app.

- Added GitHub Actions CI to run ruff check/format, regenerate synthetic data and
  features, train/evaluate/compare with SQLite MLflow, run pytest with an 80%
  coverage gate, upload `coverage.xml` and build the API Docker image.

QUALITY

- Wrote 59 tests covering cleaning, validation, metrics, leakage, batch/serving
  parity, time splits, sklearn models, PyTorch behaviour, MLflow training,
  comparison generation, promotion approval/refusal, FastAPI behaviour, drift and
  DAG structure.

- Final local verification: `ruff check .` and `ruff format --check .` clean;
  59 passed, 6 warnings; 83.17% coverage against an 80% gate.
